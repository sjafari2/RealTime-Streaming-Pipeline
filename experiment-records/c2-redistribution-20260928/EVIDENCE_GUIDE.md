# Measurement and cost evidence

This block keeps three consumers throughout. The intervention redistributes partitions; its measured disruption includes the full release/acquire/resume barrier. It is not a measurement of Kafka's default automatic rebalance or a monetary cloud bill.

| Measurement | Evidence retained | Interpretation |
|---|---|---|
| Completion mean and p99, unfinished work, deadline outcomes | Per-message producer acknowledgments and consumer start/completion records; `outcome-summary.json` | Evaluation cohort only, with completion before commit acknowledgment. Unfinished records are reported separately. Configured deadlines are experimental thresholds, not validated application requirements. |
| Input and useful throughput | Distinct message IDs, producer timestamps, acknowledgment timestamps, completion timestamps | Separate attempted input, acknowledged input and distinct completed work. Warm-up completions during evaluation remain distinguishable from evaluation-cohort outcomes. |
| Partition lag, processing backlog, growth and skew | Run-scoped `prometheus.json`, `lag-summary.json`, ownership/validity flags | Preserve partitions and owners, not only a total. Missing or stale observations remain unavailable. |
| Processing interruption | Per-message processing intervals and per-consumer release/resume events | Last pre-resume completion to first post-resume processing start; verify that no recorded processing interval overlaps the gap. Also retain the no-completion gap and each consumer's pause. |
| Coordination duration | `explicit-handoff-events.jsonl` | Release request to verified active assignment. Scheduled time, actual action time and resume request are recorded separately. |
| Work accumulated during the transition | Distinct acknowledgment and completion events | Count acknowledged-but-unfinished messages at the transition boundaries, including warm-up. Report net change during coordination and during the processing pause separately. This is not exact broker-offset lag or a causal counterfactual estimate. |
| Recovery | Valid processing-backlog observations after resume | Primary criterion: at most 100 offsets for 30 consecutive seconds while production continues. Retain 50/200-offset sensitivity checks. A brief low interval or clearance only during drain does not establish this recovery criterion. |
| Requested CPU and memory cost | Independent two-second campaign resource observer and original pod specifications | Integrate requested consumer cores and GiB over evaluation plus drain; report core-minutes, GiB-minutes and coverage. All phases remain in the raw observer for other declared accounting windows. |
| Actual process CPU and memory | Prometheus CPU/RSS samples and `measurement-audit.json` | Retain sampled peaks, time-weighted means and observed integrals for producers and consumers. CPU percent-seconds / 100 gives core-seconds. RSS byte-seconds / 2^30 gives GiB-seconds of memory footprint. Partial coverage is not zero usage. |
| Correctness and comparability | `handoff-validation.json`, `manifest.json`, final per-process evidence status | Check duplicate identities/offsets, completion identities, contiguous completed prefixes, ownership, process incarnations, original pod placement and resource settings. Preserve unfavorable valid results. |
| Reproducibility | Frozen `pipeline-configmap.yaml`, execution revision, source/evidence hashes, seed, common phase boundaries and clock probes | Keep technical checks separate from performance trials; retain timing uncertainty and collection gaps. |

The prospective definitions are in [`cost-protocol.json`](../../experiments/c2-redistribution-20260928/cost-protocol.json). Final small summaries and plots are versioned here. Per-message logs and full monitoring exports remain in the ignored `results/<run-id>/` directories; the campaign observer and reference configuration remain in `results/c2-redistribution-20260928-033632/`. Git records and hashes are not a backup of those raw files. Independent-storage backup is a separate step and is not certified by this guide.

The reports distinguish observed costs from benefits. A net backlog change during a handoff does not by itself measure the extra backlog caused by the intervention relative to a no-action trajectory. Requested resources also do not measure total cluster energy, broker cost or financial cost.
